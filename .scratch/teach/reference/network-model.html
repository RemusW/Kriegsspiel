The network model, on one page

Every message, every route, and the path a single drag takes from one umpire's mouse to another umpire's screen.

The transport split

A socket carries events: small, ordered, pushed, perishable. HTTP carries resources: large, addressable, cacheable, requested.

ChannelCarriesWhy there
ws://host:7878/wscommands up, snapshots down server must push; ordering matters
same socket, binary frameimage upload must precede the command naming it
GET /assets/{id}one image immutable URL, so cached for a year
GET /savewhole game as .ksg browser download wants a response
POST /loadwhole game replaced one large body, one reply
GET /health"ok"liveness

All HTTP routes carry permissive CORS headers, because the client is never on the game server's origin (localhost:1420 in dev, tauri://localhost packaged, the relay for a player). CORS does not apply to the WebSocket, so this is no weaker than what already holds.

Client → server: ClientMessage

crates/server/src/protocol.rs. JSON, tagged by a type field, camelCased. Every one of these is a command: it states the result it wants, not the input that produced it.

Server → client: ServerMessage

MessageFieldsWhen
snapshot board, turns: TurnInfo[], viewing: number|null on connect, and after every change this client should see. All three taken under one read lock, so the board and its label can never disagree
assetRejectedreason an upload the store would not take. Nothing stored, so the command that was going to use it will be refused too

TurnInfo is { recordedAt, pawns } — enough to list and label a turn, never the board it holds.

Effect: who gets told

Returned by apply(), the pure function the tests call directly.

ValueMeans
Nonenothing changed, nobody needs telling (e.g. undo with an empty stack)
Meonly the sender: their own view changed (stepping turns), or it was refused and their client may be showing a pending edit that never happened
Everyonethe live board changed; every connection must rebuild its own view

The invariant: a refusal still sends a board. That is what makes it impossible for a pending client-side edit to stick.

Locks, in order

Always document first, then images. Every path that needs both follows that order, which is what stops a save (reads both) deadlocking against a load (replaces both).

doc:    Arc<RwLock<Doc>>
assets: Arc<RwLock<AssetStore>>
changed: watch::Sender<()>

A lock is never held across a socket write: a slow client must never be able to stall the game. Hashing and zipping go to spawn_blocking.

The socket lifecycle

Server, per connection

1. GET /ws arrives; upgrade() raises the frame and message limits to clear the largest image, then upgrades
2. client() starts. Umpire id from next_umpire
3. changed.subscribe() — before the first send, so a change in between still wakes the loop
4. send_view() — the first snapshot, unprompted
5. loop { tokio::select! { ... } } on two branches: socket.recv() and changed.changed()
6. any error or close → break, task ends, receiver dropped

Client

1. new WebSocket(socketEndpoint()), state connecting
2. onopen → connected
3. onmessage → parse, showView into the store (or setNotice)
4. send() drops the message and returns false unless readyState === OPEN; commands are never replayed after a reconnect, because the board may have changed
5. onclose → disconnected, retry in 1500 ms, for ever
6. reconnect gets a fresh snapshot — and a new umpire id, so undo history is lost

The path of one drag

→ pointer up ends the Manipulation; past the movement threshold?
→ engine builds one place with a Placement per unit
→ PendingEdits.hold() — the screen already shows the result
→ serverConnection.send() — one JSON frame
→ client()'s socket.recv() branch wakes
→ receive() parses, takes the doc write lock, calls apply()
→ apply() validates (finite numbers, scale range, ids on board) then Doc::edit() → one undo step for this umpire
→ returns Effect::Everyone → changed.send_replace(())
→ every connection's changed.changed() branch wakes
→ each calls send_view(): its own doc.shown(umpire)
→ client onmessage → showView → store
→ engine's subscriber runs PendingEdits.settle(), pawns spring to the new positions

Rules that are easy to break

Server is authoritative there is no client-side Doc. Clients send commands and display boards.
Every edit via Doc::edit so it becomes one undo step for its umpire. Mutating doc.board directly is for setup only.
Filter on the server a player's client must never receive data for units it may not see. Never send the full board and hide it client-side.
Screen = board + PendingEdits drawing, picking and the values a new edit builds on all read the units as drawn, never board.pawns, which lags the screen by a round trip.
A drag is one undo step never a command per frame, never on mouse-down. Presence updates will be separate messages, not edits.
A command may only name a stored image so a board can never refer to an image a save would not find.
Commands are absolute, so repeats are harmless place carries the result it wants, not a delta. Deltas would not survive reordering or replay.

Not built yet

Umpire identityevery connection is a new umpire. Nothing stops a page the umpire visits from opening a socket to their own server and sending commands, or reading /save. Identity owes undo nothing: a connection ending drops its umpire entry (Doc::forget_umpire) by decision, so identity is only about who may do what. ADR 0018.
Per-side filteringdoc.shown(umpire) is the hook, but returns the whole board today. Players do not exist as a role yet.
Request ids and repliesa refusal sends a board but never says why. Needed for Step::Partial and for MCP.
Per-unit deltasconsidered and rejected, not pending: a delta needs every earlier one, which the watch channel's coalescing will not promise. Snapshots self-heal instead. If the path needs to be cheaper, serialize once per distinct view.
Presencetransient, umpires only, throttled, never part of Doc. Designed in lesson 0007, not built: its own watch<HashMap<UmpireId, Presence>> (never the changed doorbell, which would serialise a whole board per tick); holding: Vec<Placement>, because a drag is a stream of would-be commands; cleared at client()'s exit, with a staleness stamp for half-open connections. Smoothing is already solved: the springs in pawns/spring.ts chase one latest target, which is the only strategy compatible with dropping outdated updates. What is missing is a cursor layer keyed by umpire, and a second input to lifted. ADR 0021, lesson 0006.
The relayforwarding chosen over WebRTC to start with.
Backpressurethe browser WebSocket API has none; a client that cannot keep up buffers snapshots until it falls over.
