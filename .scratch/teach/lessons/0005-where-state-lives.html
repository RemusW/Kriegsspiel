Lesson 0005 · Kriegsspiel network model

Where state lives

PendingEdits is unmistakably state: a mutable Map, read every frame, deciding what is on screen. It is not in your store. Four lessons have used it without asking why, and the answer is the one piece of React worth properly understanding — because a store is not a place to keep things. It is a list of who to wake.

00First, from memory

  1. What does the same-origin policy do for your WebSocket?

    • It blocks cross-origin socket opens
    • It triggers a preflight request first
    • It does nothing at all
    • It applies only to text frames

    Nothing. It does not apply to WebSockets, there is no preflight, and CORS is never consulted. RFC 6455 §10.2 hands the duty to the server, which is why upgrade() has to check Origin itself.

  2. Why does a place command carry absolute values?

    • Deltas would need more bandwidth
    • A repeat states the same result
    • Rounding errors would accumulate faster
    • The server cannot compute offsets

    Idempotence. A command says what it wants to be true, not how far something moved, so sending it twice is harmless and a lost one can be re-sent without doubling anything.

  3. What does Doc::forget_umpire now guarantee?

    • Pending edits are discarded on reconnect
    • Another umpire cannot undo your work
    • Snapshots stop being sent to it
    • A reconnecting umpire starts with nothing

    That history lasts exactly as long as the connection (ADR 0018). Today it collects something unreachable; once an id can come back, it is the thing that enforces the rule.

01The question, put properly

Your own architecture decision says it plainly:

“Per-frame data (camera, drag positions, presence) stays inside the engine, as does PendingEdits.”

ADR 0019, client state.

Read as a rule that is easy to follow and hard to justify. selection is in the store. board is in the store. Both are “data the client holds”, and so is PendingEdits. If the store is where client state goes, leaving one map out of it looks like an exception someone made for convenience.

It is not. The three live in different places because putting something in a store is not an act of storage. It is an act of subscription. Everything below is that one sentence, unpacked.

02What a React render actually is

You know a frame loop. Yours is in KriegsspielEngine.render, driven by setAnimationLoop, and the springs under it step at a fixed 240 Hz. Its shape: you decide when to draw, you draw everything, and you do it again. Drawing a frame identical to the last one is completely normal and costs exactly what any other frame costs.

React inverts the control. You never call render. You invalidate, and React decides. The official description names three steps (React docs, Render and Commit):

  1. Trigger. “Updating your component’s state automatically queues a render.” Nothing else does, besides the first mount.
  2. Render. “Rendering is React calling your components.” Your function bodies run again, return fresh JSX, and React works out what changed.
  3. Commit. React writes to the DOM — and only the parts that differ. “React does not touch the DOM if the rendering result is the same as last time.”

Now the disanalogy, which matters more than the analogy. A frame loop is pull at a fixed rate: cost is flat, and how often your data changes is irrelevant to it. React is push at whatever rate you trigger it: cost is zero when nothing changes and the whole subscribed subtree when one value does.

The consequence worth keeping

In a frame loop, “how often does this change?” is a free question — you redraw regardless. In React it is the question, because the change rate of a value is the render rate of everything subscribed to it. Per-frame data in a push system is a category error, not an optimisation problem.

03So do the arithmetic

Follow a drag. Manipulation calls preview(), which the engine wires to two lines:

client/src/engine/KriegsspielEngine.ts:199

preview: (edits) => {
  this.pending.hold(edits);
  this.refresh();
},

And refresh() is called “when a board arrives and whenever a pending edit changes, which during a drag is every move of the pointer.” That is 60 to 120 times a second on ordinary hardware, and more on a high-rate mouse.

Its own doc comment. Worth noticing that the comment states the frequency — the author of that line knew the rate was the point.

Suppose PendingEdits lived in the store. Each pointer move becomes a set(), which is a trigger, which wakes every component holding a useClientStore subscription. Count them from GameScreen.tsx: connection, board.pawns, plus Toolbar, Timeline and FileBar. Your component functions run, allocate JSX and get diffed, at pointer rate, for the length of every drag.

Then React reaches the commit step and does nothing, correctly, because no DOM node in your application depends on a pending edit. The board did not change. The unit count did not change. The timeline did not change.

That is the precise shape of the mistake, and it is sharper than “it would be slow”: you would pay the trigger and the entire render phase to arrive at a commit phase guaranteed in advance to be empty. One hundred per cent of the cost for a benefit that is structurally zero — not usually zero, not zero on a fast machine. Zero by construction, because React draws none of it. three.js does.

04The receipt is already in your store

This is not a theoretical force, and you do not have to take my word for it, because you have already paid it twice — in showView, the function that writes each arriving snapshot into the store:

client/src/state/store.ts:105

const kept = state.selection.filter((id) => ids.has(id));
// Keep the old array when nothing was dropped, so subscribers see no selection change.
const selection =
  kept.length === state.selection.length ? state.selection : kept;

And its neighbour sameTurns, which walks the whole turn list comparing fields so it can hand back the old array when they agree. Its comment says why: “the timeline then re-renders when the history does, not on every edit anyone makes.”

Look at what those two are. Hand-written memoisation, guarding reference identity, because React and Zustand compare with === and a fresh array that means the same thing still counts as a change. Neither line is about correctness. Both exist only because the value is in the store, and both would be deleted if it were not.

That is the membership fee. selection and turns pay it because React genuinely needs them. PendingEdits does not pay it, because it never joined.

The same discipline appears on the engine side, in applyTo: if (this.edits.size === 0) return units; — the identical array back when nothing is pending, so a downstream !== check stays meaningful. Reference identity is load-bearing on both sides of the seam.

05The rule, in a form that transfers

Three questions, asked in this order. The first “no” decides it.

  1. How often does it change? Pointer rate or frame rate → not in the store, and stop here.
  2. Does any rendered output depend on it? If no DOM node reads it, the store can only ever cost you.
  3. Does anything outside its owner need to read it? If only the engine touches it, the store is doing no work for you.

Run the four pieces of state through it:

PendingEditspointer rate · nothing in the DOM · engine only. Three noes. Engine.
boardnetwork rate, human-paced · GameScreen prints the unit count · React and the engine both read it. Store.
selectionhuman-paced · drives what the tools offer · read in both places. Store, and it pays its fee in showView.
cameraevery frame · nothing in the DOM · the rig alone. Engine, by the same three noes as PendingEdits.
Say this one in an interview

PendingEdits is to the client store what presence is to the server’s Doc. Your own notes say presence “is not part of Doc, not saved and not undoable”; a drag still ends in one edit command, and the 20 Hz stream in between is deliberately kept outside the document. Identical reasoning, opposite end of the wire: high-frequency, transient, nobody else’s business — so keep it out of the thing that notifies everyone.

One principle, applied twice, in two languages. That is a far better answer than reciting what Zustand is.

06How the engine reads the store at all

A fair question, since the engine is not a component and cannot call a hook. In App.tsx it is handed the store object directly, and it uses the two methods React never sees:

client/src/engine/KriegsspielEngine.ts:119

this.unsubscribe = store.subscribe((state, previous) => {
  if (state.board !== previous.board) {
    this.pending.settle();
    this.refresh();
    this.syncMaps();
  }
  ...
});

getState() to read now, subscribe() to be told later. No hook, no render, no component. And notice the shape of that callback: a chain of !== comparisons against the previous state, each guarding its own piece of work. That is the manual version of what a hook’s selector does for a component — which is exactly why reference identity had to be preserved upstream in showView.

The boundary is clean in both directions: React owns the DOM, the engine owns the canvas. App.tsx constructs the engine once in a useEffect with an empty dependency array, and keeps the canvas mounted on every screen, so switching from the menu to the game does not touch it.

Its comment says so: “Unmounting it would run the effect’s cleanup and dispose the engine.” The engine outlives every React tree above it.

07What this costs you

It is a trade, so here is the other side, honestly.

  1. React cannot see pending state. If you ever want the UI to say “2 edits in flight” or grey out a control while one is, you will need a deliberate bridge. Nothing wants it today — and when something does, the answer is to publish a small derived summary into the store, not to move the map.
  2. There are two sources of truth for what is on screen. A reader has to know that shown is not board.pawns. That you have an entire architecture rule devoted to repeating this (“What is on screen is the board plus PendingEdits”) is the cost made visible.
  3. Devtools and time travel do not see it. A store snapshot does not describe the screen during a drag, which is worth knowing before you debug one.

08Recall

  1. What does a Zustand set() actually cost you?

    • A write to browser memory
    • A diff of the whole board
    • A render of every subscriber
    • A copy of the state tree

    A trigger. The storage is free; the notification is the price. That is why the question is always “who is subscribed, and how often does this change?”

  2. During a drag, how often is refresh() called?

    • Once when the drag begins
    • Once per animation frame drawn
    • Once when the drag releases
    • Once per pointer move event

    Per pointer move, which is where the rate comes from. The command is sent once, at the end — one drag, one undo step — but the preview updates on every move.

  3. If pending edits were in the store, what would React commit?

    • Every unit position, each frame
    • Nothing, because the DOM matched
    • Only the units being dragged
    • The selection and the toolbar

    Nothing at all. React does not touch the DOM when the rendering result is unchanged — so you would pay the trigger and the whole render phase for a guaranteed-empty commit.

  4. Why does sameTurns exist in showView?

    • Turn lists arrive out of order
    • The server sends turns too often
    • A new array would re-render Timeline
    • Zustand cannot compare nested arrays

    Reference identity. Every snapshot carries the turn list, but it rarely changes; handing back the old array keeps subscribers asleep. It is the membership fee for being in the store.

  5. What is PendingEdits the client-side twin of?

    • The server's recorded turn history
    • Presence, which is not in Doc
    • The watch channel's coalescing doorbell
    • The per-umpire undo and redo stacks

    Presence. High-frequency, transient, nobody else's business, so it is deliberately kept out of the structure that notifies everyone. Same principle, other end of the wire.

09Drill: where does it live, and why?

The reason matters more than the answer here. Two of these have a right home for a wrong reason among the options.

  1. The camera's position and heading.

    • The store: the toolbar shows it
    • The engine: nothing rendered reads it
    • The store: screens must restore it
    • The engine: three.js owns the data

    Engine — but because no DOM node depends on it and it changes every frame, not because three.js happens to hold it. “The library owns it” is a coincidence; the change rate is the reason. cameraMode, meanwhile, is in the store: the toolbar sets it, and it changes when a person clicks.

  2. Which recorded turn this umpire is viewing.

    • The engine: it changes what is drawn
    • The engine: the server already tracks it
    • The store: the timeline must label it
    • The store: it changes on every frame

    Store. It does change what is drawn, and the server does track it, but neither decides: the Timeline has to render which turn is on screen, and EditorContext.readOnly turns off the tools. React needs it, so it is in the store, and it changes only when a person steps.

  3. The marquee rectangle being dragged out right now.

    • The store: the toolbar sets its shape
    • The store: the selection depends on it
    • The engine: it must survive reconnects
    • The engine: it changes at pointer rate

    Engine, on question one. Your conventions already say the box “never goes through the store”. Note the trap: marqueeShape is in the store, the rectangle is not — one is a human choice, the other is a pointer position, and they are not the same kind of thing despite sharing a name.

  4. Whether the socket is connected.

    • The store: GameScreen renders the text
    • The engine: the socket lives nearby
    • The engine: it changes too often
    • The store: it must be undoable

    Store, on question two: there is a DOM node showing it. It also changes about as rarely as anything in the app. Note that it is not game state — it is in the client store and nowhere near Doc, which is the third place this distinction has turned up.

10Read this next

React docs — Render and Commit. Short, official, and the source of every claim above about what a render is. Read it with one question in mind: what triggers step one? The page is emphatic that only a state update does, and that is the whole reason the change rate of a value decides where it belongs.

Then, if you want the other half, State as a Snapshot explains why a render sees the state it was triggered with — which is the bit that bites people coming from a frame loop, where you read a mutable position whenever you like.

Both pages are on react.dev, the maintainers' own documentation. For the store side, Zustand's vanilla createStore reference covers getState and subscribe, the two methods the engine uses.

11Next

Lesson 6 — smoothing what arrives late. The natural sequel, and the one place your existing skills do most of the work. Boards arrive at human pace from a few hundred milliseconds away, and pawns/spring.ts already interpolates towards them at a fixed 240 Hz step. That machinery is most of what presence needs — a 20 Hz stream of another umpire's drag, smoothed between updates, outdated ones dropped rather than queued. The networking name for it is entity interpolation, and Gambetta Part III is the primary source.

To say out loud before then: "a store is not storage, it is a subscription — so the change rate of a value is the render rate of everything reading it".

Ask me. Three worth pushing on. What the bridge looks like if you do want pending state in the UI — it is a real design question and the obvious answer is the wrong one. Why PendingEdits cannot cover spawns and deletions, which is structural rather than an oversight, and the best remaining gap in the optimistic-update story. And whether the engine should subscribe at all, or be told — the callback at line 119 is a small inversion-of-control decision that could have gone the other way.
