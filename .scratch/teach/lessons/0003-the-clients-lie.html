Lesson 0003 · Kriegsspiel network model

The client's lie

Only the server moves units. Yet the piece follows your mouse with no delay at all. The client is showing you something that has not happened — and the engineering is not in telling the lie, it is in guaranteeing it can never get stuck.

00First, from memory

  1. Why does the watch channel carry no data?

    • Unit types cannot cross a channel
    • Sending data would block the writer
    • No one board suits every client
    • The document lock forbids holding it

    Umpires view different turns, and players will get filtered boards, so there is nothing correct to put in one shared message. Doorbell, not delivery. Each connection then builds its own view from doc.shown(umpire).

  2. Why does send_view drop the lock before writing?

    • Writes need a mutable document borrow
    • A stalled client would freeze everyone
    • Snapshots must be built while unlocked
    • The watch channel reacquires it later

    A socket write to a stalled client can block for a long time. Holding a read lock through it stops any writer taking the document, so nobody can edit until that one client's network recovers. The other reason to read everything under one lock is that the board and the viewing index that labels it cannot then disagree.

01The problem, in one number

A few hundred milliseconds through the relay. Now consider what your own architecture rules insist on: every edit goes through Doc::edit on the server, and there is no client-side Doc. Taken literally, the honest client is this: you drag a piece, nothing happens, and 300 ms later the piece arrives where you left off.

300 ms is an estimate in CLAUDE.md, never measured. It is also roughly 18 frames at 60 Hz, which is a useful way to feel it: the piece would be the better part of a third of a second behind your hand, continuously, for the whole drag.

That is unusable, and notice it is unusable only for some operations. Recording a turn can take 300 ms and nobody minds. Dragging cannot. The dividing line is whether the action is continuous and hand-guided: anything tracking a pointer has to be immediate, because the feedback loop is your own proprioception and you will notice tens of milliseconds.

So one of the two rules has to bend. The one that bends is not server authority — it is the assumption that the screen shows the board.

The rule that replaces it

What is on screen is the board plus the edits this client has asked for and not yet seen come back. Drawing, picking, and the values a new edit builds on all read the units as drawn — never board.pawns, which lags the screen by a round trip.

02What the textbook does, and what you did instead

The standard reference for this problem is Gabriel Gambetta's, and it is worth knowing precisely because your solution is not the one he describes. Being able to say why is the valuable part.

His setting is a player running around a simulated world. The client “predict[s] what the game state will be after the server has processed the inputs”, which works “because the game world is deterministic”. Reconciling that prediction then needs real machinery:

“First, the client adds a sequence number to each request… Then, when the server replies, it includes the sequence number of the last input it processed.” The client adopts the server's state and re-applies “all the input still not seen by the server.”

Gabriel Gambetta, Client-Side Prediction and Server Reconciliation

Sequence numbers, a saved queue of unacknowledged inputs, and a re-simulation on every server update. PendingEdits.ts is 60 lines and has none of that. The reason is two design choices you already made, probably without framing them this way.

One: commands are absolute, not inputs

Gambetta's client sends inputs — "held right for 16 ms" — which only mean something when a simulation integrates them, in order, from a known starting state. Miss one, or apply them out of order, and the result is wrong. Hence sequence numbers.

The doc comment on Placement already says this: "Every value is absolute, so a command states the result it wants instead of how far a pointer or key moved it." That sentence is the reason this lesson is short.

Your client sends a result: Placement { id, pos, rot, scale }. Absolute. Which means the client is not predicting anything — it already knows the exact value it asked for, because it chose it. There is nothing to re-derive when the answer comes back.

Two: there is no simulation to be out of step with

The server does not integrate physics. It validates and assigns. So the server's result is not an approximation of the client's guess that might drift — given a command that is accepted, it is byte-identical to what the client drew. Divergence is not a spectrum here; it is binary. Either the command was applied, or it was refused.

Name it correctly

This is an optimistic update, not client-side prediction. The client shows the result it has asked for, on the assumption that permission will be granted. Reconciliation is therefore not a re-simulation. It is one sentence: stop lying when the truth arrives.

03The whole mechanism

Three methods carry it. hold starts showing an edit, settle stops, and applyTo is the overlay itself:

/** These units as they are drawn. The same array comes back when nothing is pending. */
applyTo(units: readonly Unit[]): readonly Unit[] {
  if (this.edits.size === 0) return units;
  return units.map((unit) => {
    const edit = this.edits.get(unit.id);
    return edit ? { ...unit, ...edit } : unit;
  });
}

client/src/engine/PendingEdits.ts

A field-level overlay, not a replacement: previewOf copies only the fields a Placement actually carries, so a turn-only manipulation overrides rot and leaves pos reading from the board. If it replaced whole units, a board arriving mid-turn with someone else's position change for that unit would be discarded.

Returning the identical array when nothing is pending is not a micro- optimisation — it keeps referential equality, so subscribers comparing by identity see no change. Same discipline as sameTurns in the store.

And one line wires it to the server's boards:

if (state.board !== previous.board) {
  // This board answers every pending edit no gesture is still holding.
  this.pending.settle();
  this.refresh();
  this.syncMaps();
}

04The invariant, and the four ways it could break

A pending edit is a claim about the future. If one ever gets stuck, that unit is drawn somewhere it is not, for ever, and every subsequent edit is measured from a fiction. So the invariant is absolute:

Every pending edit is removed, in bounded time, whatever happens.

There are exactly four ways that could fail, and each is closed by a line or two. This is the part to be able to recite.

  1. The server refuses the command. An off-map position, a bad scale, an id that no longer exists — or the umpire is viewing a recorded turn. Nothing changes on the board, so no board would be sent, so settle() never runs and the lie is permanent.

    Closed on the server, by lesson 2's Effect::Me: a refusal still sends that umpire a board. That is what the enum value is for. The client needs no refusal-handling code at all, which is why you will not find any.

  2. The command is never sent. The socket is down. ServerConnection.send returns false rather than queueing, on purpose: "replaying commands after a reconnect could apply them to a board that has changed since."

    } else if (this.host.send(this.placements())) {
  this.host.releasePreview();   // sent: the edit stands until a board answers it
} else {
  this.host.discardPreview();   // not sent: nothing will ever answer it
}

    client/src/engine/Manipulation.ts, leave()

    The return value of send is load-bearing. Ignore it and a drag made while disconnected sticks for ever.

  3. Nothing actually changed. A click, or a drag that ends where it began. isIdentity() discards the preview and sends no command at all — which also keeps empty undo steps out of the umpire's history.
  4. Someone else's board arrives mid-drag. The nasty one. Another umpire edits a different unit; their board reaches you while your drag is still under way; settle() runs and clears your in-flight edit, so the piece you are holding snaps back to the pointer's starting position.

    Closed by the held set: settle() deletes every pending edit except the ones a running gesture is holding. release() hands them over once the command is sent, and they settle on the next board like any other.

Four states, and the whole lifecycle of a pending edit is their transitions: hold → (discard | release → settle). There is no fifth path, which is the actual proof that the lie cannot stick.

05The failure that makes this non-optional

It would be easy to read all of the above as a polish feature — the piece looks nicer following the mouse. It is not. Look at where a manipulation gets its starting values:

"The units as drawn when the manipulation began." this.shown, which is pending.applyTo(board.pawns). Not board.pawns.

const starts = this.shown.filter((unit) => selected.has(unit.id));

client/src/engine/KriegsspielEngine.ts:196

Suppose it read board.pawns instead. Drag a unit 10 m east and let go. Now, inside the same 300 ms, drag it 10 m north. The second manipulation starts from the board, which still has the unit at its original position, and sends "put it 10 m north of where it started" — absolute, remember. The east move is silently erased. Two deliberate edits, one survives.

The same bug in picking: click where a piece visibly is mid-flight and, reading the board, you select whatever used to be there. This is why the rule names all three consumers — drawn, picked, and measured from. Getting two of the three right is the bug that is hardest to find.

Worth noticing

PawnLayer's springs are a fourth thing, and deliberately not in this list. Blocks lag their units visually, lean into a drag, bounce on landing — and picking and edits ignore all of it, using exact positions. So there are three layers of truth on screen: the board, the board plus pending, and the springs' rendering of it. Only the middle one is ever picked against or measured from.

06Recall

  1. Why does this client need no sequence numbers?

    • The socket cannot reorder messages
    • Only one command is outstanding
    • The server replies to each command
    • Commands carry absolute values

    A place states the result, not an input to be integrated, so there is no simulation to replay and nothing to re-derive from acknowledged inputs. Ordering does hold, but it is not the reason; a delta-based command would need sequence numbers even over an ordered socket, because the client would have to know which deltas the server had folded in.

  2. What clears a pending edit after a refused command?

    • The board that a refusal sends
    • A timeout in the pending edits
    • An error message from the server
    • The next successful command sent

    Effect::Me: a refusal still sends that umpire a board, and any board runs settle(). There is no timeout and no refusal message — the client has no refusal-handling path, by design. Note what is still missing: the umpire learns the edit did not happen, but never why.

  3. Why does a running gesture keep its own pending edits?

    • Its edits are not yet complete
    • Gestures may send several commands
    • Another board would clear them
    • The server has not seen them

    Any board arriving triggers settle(). Without the held set, an unrelated edit by another umpire would clear the drag you are in the middle of, snapping the piece back to where it started. The server has indeed not seen them — but that is true of released edits too, and those settle normally.

  4. Why must a manipulation start from the units as drawn?

    • The board omits selected units
    • A second edit would erase the first
    • Drawn positions include spring motion
    • The board is read-only to tools

    Commands are absolute, so an edit built on the stale board states a result computed from the wrong starting point and silently reverts the edit still in flight. Option 3 is a real distinction but the wrong way round: spring positions are excluded, since picking and edits use exact values.

  5. What does the client do with a command it cannot send?

    • Queues it until reconnection happens
    • Retries it on a short timer
    • Drops it and discards the preview
    • Applies it to the stored board

    send returns false and Manipulation.leave calls discardPreview(). Deliberately not queued: a replayed command carries absolute values computed against a board that may have changed while you were disconnected, so replaying it could stamp on someone else's work.

07Drill: the lie gets stuck

In each case a unit ends up drawn somewhere it is not, permanently. Which change caused it?

  1. A drag made while the connection is down leaves the piece floating at the drop point for ever.

    • settle() stopped sparing held edits
    • The result of send is ignored
    • previewOf copied every field
    • applyTo returned a new array

    With nothing sent, no board will ever arrive to answer that edit, so release() leaves it pending until the page is reloaded. The whole reason send returns a boolean is to distinguish this from a successful send.

  2. The server refuses a scale of 9, and the unit stays drawn nine times too large.

    • The client stopped validating scale
    • The gesture never called release
    • applyTo skipped unknown ids
    • apply returned Effect::None

    A refusal must answer its sender. Return None instead of Me and nothing is sent, so settle() never runs. This is the coupling worth remembering: a client-side invariant enforced by a server-side enum. Clamping on the client would hide it, not fix it.

  3. While one umpire drags, another umpire's unrelated edit makes the dragged piece snap back to its origin.

    • settle() cleared the held edits
    • hold() replaced the edit map
    • The board arrived before the command
    • Effect::Everyone woke the sender

    Exactly the case the held set exists for. Note this one is not permanent — it resolves when the drag ends — but it is the most noticeable failure of the four, and it only appears with two umpires connected, which is why it is easy to ship.
