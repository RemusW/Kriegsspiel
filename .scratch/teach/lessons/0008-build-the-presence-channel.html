Lesson 0008 · Kriegsspiel network model

Build it: the presence channel

Seven lessons of reading and one of design. This one you write. The design is already settled — 0007 chose the channel, the payload and the cleanup — so nothing here is a puzzle about what to build. What is left is the part that only transfers by doing it: getting a second channel into a live socket loop without breaking the one already there.

00First, from memory

  1. Why can presence not travel on the changed channel?

    • Each ring serialises a whole board
    • The channel carries no payload data
    • Watch channels coalesce the updates away
    • Umpires would receive their own cursors

    Because of what each connection does when the doorbell rings: it calls send_view, which serialises an entire board. Carrying no payload is true but fixable; the cost at the other end is not.

  2. What does a lagging broadcast receiver get?

    • Lagged, then the newest value only
    • Lagged, then the oldest retained value
    • Nothing, because the sender blocks
    • Lagged, then a full resync message

    The oldest value still in the ring, so it walks a backlog of stale frames before reaching the present. Sequence-preserving, which is the opposite of what a cursor wants.

  3. What makes a connection's cleanup provable, not hopeful?

    • A Drop guard on the socket
    • A periodic sweep over the umpires
    • One exit point every path meets
    • A heartbeat timing the umpire out

    One exit point. A Drop guard cannot work here at all: the document sits behind a tokio lock, and locking it from Drop would mean blocking_write inside the runtime, which panics.

01What you are building, and what you are not

Held pieces only. No cursors.

A manipulation has exactly two interesting moments — it starts and it ends — so the held-pieces half of presence is human-paced and needs no throttling at all. Two messages per drag. Cursors need the 20 Hz stream, a throttle, and a decision about smoothing: a second problem, and a worse first exercise.

It is also the half your own CLAUDE.md justifies on its own terms — “so two umpires do not grab the same piece unawares”. Cursors are pleasant. This one prevents a collision.

Scope, then: the server learns what each umpire is holding, tells the others, and forgets it when a connection ends. The client half is a stretch goal at the bottom, and deliberately unspecified.

02How you will know it works

Six tests are waiting in .scratch/teach/exercises/0001-presence-tests.rs. Paste the whole block inside the existing mod tests in crates/server/src/lib.rs, above placement_json_leaves_out_unset_fields. Then:

cargo test -p kriegsspiel-server presence

It will not compile, and that is the first instruction: the compiler names the thing that does not exist yet. Work down the tasks until all six pass. Run the whole suite before you commit, since that is what regenerates client/src/bindings/.

What the tests deliberately cannot reach

None of them opens a socket. Testing the select! arm would mean binding a port and taking a WebSocket client as a dev-dependency, and this repository has chosen not to — the HTTP tests go through the router with tower's oneshot instead. So the loop is untested here, which is exactly why ADR 0021 made apply “a plain function the tests call directly”. Push every decision out of the loop into something a test can call, and leave the loop holding nothing worth testing. That principle is the real subject of tasks 3 to 6.

03Task 1 — the two messages

The tests pin the wire format, because they send raw JSON:

client → server   {"type":"presence","holding":[{"id":0,"pos":[1,2]}]}
server → client   {"type":"presence","holding":[ ... ]}

One variant on each of ClientMessage and ServerMessage in crates/server/src/protocol.rs, both carrying Vec<Placement>. Match the file's house style: the serde and ts-rs attributes sit on the enums already, so a variant needs none of its own.

A question worth answering before you type. The same name points both ways and means something different each way: outbound it is what I am holding, inbound it is what everybody else is holding. Is that acceptable, or should one of them be called something else?

I think it is acceptable, because every message in this protocol is already written from the receiver's point of view — a snapshot is “your view”, not “the board”. But decide it rather than inherit it.

The declarations

On ServerMessage:

/// What the other umpires are holding: the placements their drags would send if
/// they ended now, flattened into one list. The receiver's own holdings are left
/// out, since it is already drawing its own drag.
///
/// For drawing only. These placements are in no board and may never reach one.
Presence { holding: Vec<Placement> },

On ClientMessage:

/// What this umpire is holding: the placements its manipulation would send if it
/// ended now. An empty list means it is holding nothing.
///
/// Not an edit. It changes no board, is not undoable and is never saved.
Presence { holding: Vec<Placement> },

04Task 2 — the channel

Write the field declaration for Game before you open the hint. One line. You settled the channel type in 0007 and the warm-up just asked you why.

Three things to decide, and the test file quietly assumes all three:

  1. Which primitive. Latest-only or sequence-preserving? A slow client that falls behind a 20 Hz stream should see fewer frames, never a backlog.
  2. Keyed or flat. One umpire's connection ends. What has to happen to the value, and what does that demand of its shape?
  3. In Doc or in Game. Rule one of the brief answers this, and getting it right is what keeps save.rs and model.rs out of this exercise entirely.
The field 
/// What each umpire is holding right now, for the others to draw. Unlike the
/// document this channel carries its whole value, because there is no filtering to
/// do and the value is a handful of placements; an umpire holding nothing has no
/// entry.
///
/// Not in `Doc`: presence is transient, never saved and never undoable, so it takes
/// no document lock and cannot be left behind in a save.
presence: watch::Sender<HashMap<UmpireId, Vec<Placement>>>,

Keyed by umpire, because a departure has to clear one entry. Not a Mutex, because nothing would wake the connections. Not broadcast, for the reason in the warm-up. And it needs initialising in with_assets alongside changed.

05Task 3 — set_presence

Two tests describe it, and both are about silence:

  1. an_umpire_holding_nothing_has_no_entry — holding nothing means absent, not an empty list. Ask what a client connecting ten minutes later would be told otherwise.
  2. an_unchanged_holding_wakes_nobody — a repeated holding must wake no one. This is the test that makes you read the API properly.

watch::Sender offers send, send_replace, send_modify and send_if_modified. Three of those notify unconditionally. Only one can express rule two, and the shape of its closure tells you how.

Note what you are not allowed to do: read the map, clone it, change your entry, send the clone back. That is a read-modify-write race — two umpires moving at once, and one of them disappears from the map.

The same hazard as any other compare-and-swap, met here by accident rather than on purpose. The API hands you the fix, provided you pick the right method.

Which method, and the shape

send_if_modified. Its closure is FnOnce(&mut T) -> bool, and that bool decides whether anyone is woken, so the decision happens inside the lock with the current value in hand. The body has three outcomes: nothing held and an entry existed (remove it, notify); the entry already equals this holding (notify nobody); otherwise insert and notify. Placement derives PartialEq, so comparing two holdings is one ==.

06Task 4 — others_holding

A free function, not a method: given the map and one umpire, every other umpire's placements as one list. Four lines of iterator.

The design point is in the exclusion, not the code. Leaving out the receiver's own entry is what keeps UmpireId off the wire — and it is off the wire today, everywhere. A client needs to know that a piece is held by somebody else, not by whom. The day you want named cursors you will have to put an identifier in the protocol, and it should be a per-connection label rather than this one.

One snag you will hit

Edition 2024 match ergonomics: a reference pattern such as |(&id, _)| is refused in a closure over iter(). Bind by reference and dereference in the body instead.

07Task 5 — keeping it out of the document

Presence must never take the document lock. Find where in Game::receive that has to be enforced, and notice that where is the whole answer: anywhere after the let effect = { block has already acquired a write lock on the document in order to decide it was not needed.

Then two judgment calls the tests encode:

  1. What Effect does presence return? Compare with Place, which answers Effect::Me when it refuses, so the sender can clear a pending edit it is showing. Is there anything to clear here?
  2. A broken value is dropped, not refused. Validate with the same valid_placement the commands use, then throw the message away silently. Work out why dropping is right, and — harder — why relaying one infinity onward would be worse than refusing a command. The answer is in spring.ts.

One more thing will happen here, and it is worth stopping to look at rather than silencing. apply matches ClientMessage exhaustively, so the compiler will demand an arm for the variant you just added — a variant that is never meant to reach apply at all. Whatever you write there, a comment is now the only thing keeping presence out of the document. Decide whether that bothers you enough to do something about it, and if so, what.

08Checkpoint

Six green. If you stop here you have a server that knows who is holding what and tells nobody — a real, tested, committable half, and the half the tests can defend. Everything below is the untested part.

09Task 6 — the second arm

Now serve_client: a subscription, an arm in the select!, and a sender. Three traps, and each is a question you should be able to answer before writing the line that avoids it.

  1. Why must the first presence message be sent by hand? One sentence already in the loop is the clue — the comment above let mut changed = game.changed.subscribe();.
  2. Why can the send not be one expression? As in send(socket, &Presence { holding: others_holding(&game.presence.borrow(), umpire) }).await. Something in there is a lock, and something in there is an await.
  3. What happens to a slow client under a 20 Hz stream? Trace it. This is the payoff for task 2, and the strongest single thing you can say about this design out loud.
The three answers

One. subscribe marks the current value as already seen, so changed() will not fire for the state that existed when you subscribed. Without an explicit first send, a client joining mid-drag sees nothing held until somebody moves.

Two. The borrow is a read guard on the channel's internal lock, and it would live to the end of the statement — across the socket write. Build the message in a statement of its own so the guard drops, then await. The same discipline as send_view releasing the document lock before sending, and for the same reason: a slow client must never hold a lock.

Three. Nothing bad, and that is the whole argument. The channel holds one value, so a client that is not keeping up misses intermediate states and reads the latest when it arrives. No per-connection queue, no unbounded memory, no backpressure. That is what “drop outdated ones instead of queueing them” buys, and why the brief asked for it.

10Task 7 — the vanishing umpire

One line, and you built the place for it last session. An umpire's lid closes mid-drag; their pieces must not hang in the air for everyone else.

Two details worth noticing as you write it. It is not async, unlike forget_umpire — presence is not in the document, so there is no lock to wait for. And it can share the code path with “holding nothing”, which is worth doing: one rule, enforced in one place.

What this does not close is a half-open connection, where the socket stays notionally alive for minutes after the client has gone. Structural cleanup cannot see that, and no amount of care at the exit point will fix it.

The second layer is a staleness stamp, and the ordering matters: cleanup is the mechanism, staleness is the fallback. Staleness alone would leave a ghost for the whole timeout on every ordinary disconnect.

11Stretch — the client half

Deliberately unspecified, because the interesting part is a seam decision rather than code. Three questions, in order:

  1. Where does the message enter the client? Not the store — ADR 0019 names presence as engine-side. So ServerConnection, which today only ever writes into the store, needs something new.
  2. Where do the held ids end up? PawnLayer already takes a set of lifted ids every frame. There is a method beside it that is the exact pattern you want for the stored version: find it.
  3. Why must this not go through PendingEdits? The one to get right. Follow this.shown and list everything that reads it.
The answer to the third, because it is the trap

shown feeds Picker and EditorContext.units() — what CLAUDE.md calls “the values a new edit builds on”. Put another umpire's uncommitted drag in there and your next place command is computed from a position the server has never seen. If they cancel the drag, you have moved a piece to coordinates that never existed.

PawnLayer is the right home because its own doc comment already says “This is drawing only”, and the precedent is there: the springs draw every block away from its unit constantly, and picking uses the exact positions regardless. A remotely-held block is the same category of thing.

12Say it aloud

When the tests are green, answer these from memory, out loud, without the page:

  1. Why presence gets its own channel, in terms of what the other one costs.
  2. Why that channel is latest-only, in terms of what a slow client does.
  3. Why a departed umpire's pieces fall, in terms of where the code for it lives.

Those three are the whole design, and they are the version an interviewer can follow.

Ask me. Stuck on a task, or green and wanting the implementation reviewed — the second is the more useful of the two. I have deliberately left no worked solution anywhere in this workspace, so a review will be me reading what you wrote.

Also fair game: whether the apply arm in task 5 should be solved with a type rather than a comment, and whether validating presence at all is the right call when it changes nothing.
