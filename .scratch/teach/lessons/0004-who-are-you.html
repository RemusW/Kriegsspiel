Lesson 0004 · Kriegsspiel network model

Who are you?

One line hands out identity: next_umpire.fetch_add(1). Three lessons have leaned on it. It is also the load-bearing assumption in the whole model, and it is wrong in three separate ways — one of which is a real hole, not a theoretical one.

00First, from memory

  1. Why does this client need no sequence numbers?

    • The socket guarantees message order
    • Its commands state absolute results
    • Only one command is ever outstanding
    • The server acknowledges every command

    A place says where the unit goes, not how far the pointer moved, so there is no simulation to replay and nothing to re-derive. Ordering is true but is not the reason — a delta-based command would need sequence numbers even over a perfectly ordered socket.

  2. What stops a refused edit staying on screen for ever?

    • A timeout on each pending edit
    • The next command that is accepted
    • An error reply from the server
    • A board sent to the sender alone

    Effect::Me. A refusal still sends that umpire a board, and any board runs settle(). A server-side enum enforcing a client-side invariant — which is why the client has no refusal-handling code at all.

01What identity is actually holding up

Worth listing before pulling on it, because it is more than you might think. Everything keyed by UmpireId:

Kept per umpireWhich means
undo: Vec<Edit>, redo: Vec<Edit> Ctrl+Z takes back your last edit, not whoever edited most recently
viewing: Option<usize> you can study turn 3 while a colleague keeps editing the live board
which socket gets Effect::Me a refusal reaches the umpire who caused it and nobody else
(planned) which side you may see the entire filtering rule rests on knowing who is asking
(planned) your cursor and held pieces presence is meaningless without stable identities to attach it to

So identity is not a login feature bolted on the side. It is the key that per-umpire state is stored under, and two of the five rows are things you have not built yet — which is the real reason this lesson comes before step 4 and step 5 rather than after.

UmpireId is a bare u64 (model.rs:34). Nothing about it is secret, structured or verifiable. That is fine for a map key and is exactly the problem for everything else.

02The honest reconnect

Dropped connections are normal over long distances, so look at what the client does:

socket.onclose = () => {
  // A socket that `disconnect` closed has already been replaced or dropped.
  if (this.socket !== socket) return;
  setConnection("disconnected");
  this.retry = setTimeout(() => this.open(), RETRY_MS);
};

client/src/net/ServerConnection.ts

Reconnect every 1500 ms, for ever, and replay nothing. The deliberate omission is the interesting part, and lesson 3 earned the reason: a dropped place carries absolute values computed against a board that may have moved while you were away. Replaying it would stamp on whatever happened in the meantime. So the client drops it and discards the preview, and the fresh snapshot on reconnect is the recovery. Nothing is repaired because nothing is remembered.

The property doing the work

A reconnection needs no special code path because a new connection and a reconnection are the same thing: subscribe, then send the whole state, unprompted. Self-healing snapshots again (lesson 2) — the same property that made per-unit deltas the wrong trade is what makes recovery free here.

03Three things that go wrong

One: your undo history is gone, and it is unreachable rather than lost

// Every connection is a new umpire until umpires can identify themselves.
let umpire = game.next_umpire.fetch_add(1, Ordering::Relaxed);

crates/server/src/lib.rs:464

Blink your wifi and you come back as umpire 7. Umpire 3's undo stack is still sitting in Doc::umpires, intact, with every one of your edits in it — and no connection will ever again present the id that opens it. Ctrl+Z now does nothing, for the rest of the game, however many edits you had made.

Worse than it sounds in one specific way: it is silent. The board is correct, the snapshot arrives, the UI shows connected. The only symptom is that undo quietly stops working, which a user will read as a bug in undo.

Two: nothing ever frees the abandoned umpire

Fixed since this lesson — 23 Nov 2026

This one is closed. Doc::forget_umpire now drops the entry when the connection ends, collected in client() after a new serve_client holding the loop, so the five exits below meet in one place.

Read the rest anyway, because the interesting part is what the fix turned out to rest on. I argued that identity would make this removal into data loss and that it would need a grace period. Wrong, and the codebase said so: pack takes only the board, the turns and the images, and loading a save clears every history. Undo was never game state. The owner's decision is that losing a connection loses the history, identity or not (ADR 0018) — so this line is garbage collection today and becomes the thing that enforces that rule the moment an id can come back. The real cost is not lost work, it is Step::Empty being Effect::None: Ctrl+Z after a reconnect sends nothing at all, so the key just looks broken. See learning record 0003.

Look for the cleanup and there is none. Doc::umpires is a HashMap touched only through entry(umpire).or_default(), at four call sites. No remove, no retain. The client() task ends, its socket is dropped, and the document keeps the entry for ever.

Each abandoned entry holds up to 200 Edits — the cap from push_capped — and every Edit holds Change<Unit> and Change<MapImage> values with both the before and after clones in them. So the leak is per reconnection, not per session: a flaky link over a long game adds an entry every time it blinks.

I am not going to put a number on it, because nothing here has been measured and this file's own convention is to say so. The shape is what matters: bounded per umpire, unbounded in the number of umpires, and growing with exactly the event that is described as normal.

Note that this is not in your open questions. The identity gap is recorded; this consequence of it is not. It is also the easier of the two to fix, and the fix is mostly a decision: an entry with an empty undo and redo stack and no viewing is indistinguishable from one that never existed, so it can be dropped when its connection ends — but only once you have decided that a disconnection really does abandon that history, which is the same decision as the one above.

Three: anyone can be an umpire

This is the one that is a hole rather than an inconvenience, and your own notes say so:

“nothing stops a page the umpire happens to be visiting from opening a WebSocket to their own server and sending commands, or from reading /save.”

CLAUDE.md, Open questions

That sentence is correct and it is worth understanding the mechanism properly, because three plausible-sounding defences do not apply.

04Why the three obvious defences do not hold

  1. "It is bound to loopback." True — and irrelevant, because the attacker's code is not on the network. It is JavaScript running in the umpire's own browser, on a page they opened. From there, 127.0.0.1 is reachable like any other host. Binding to loopback keeps out the internet; it does not keep out the browser sitting on the machine.
  2. "CORS protects the HTTP routes." The opposite. CORS is a mechanism for relaxing the same-origin policy, and cors() relaxes it as far as it goes: allow_origin(Any). So a page on any origin may read GET /save — the entire game, both sides' positions, every image. Your own comment is clear-eyed that this is deliberate and that being strict there "would only move the hole, not close it". Correct. But it is worth being precise that CORS was never a defence being given up: it is an allowance being granted.
  3. "The WebSocket is at least same-origin protected." No — and this is the part most people get wrong. The same-origin policy does not apply to WebSocket connections. A page on any origin may open a socket to any host and port, and no preflight is involved. CORS headers are irrelevant because CORS is not consulted.

    The protocol's answer is to put the decision on the server, and RFC 6455 is explicit about both the duty and the threat:

    A server “SHOULD verify the |Origin| field is an origin they expect”, and if not, “it SHOULD respond to the WebSocket handshake with a reply containing HTTP 403 Forbidden status code”. The purpose: “ensure that trusted browsers under the control of potentially malicious JavaScript cannot fake a WebSocket handshake”.

    RFC 6455 §10.2, Origin Considerations

    upgrade() does not look at Origin. It sets two size limits and upgrades.

05What I would do, and in what order

A recommendation, not a decision — your open question, and the design is yours. But the ordering matters more than the choice, because one of these is cheap and immediate and the other needs thought.

First, check Origin on the upgrade. A handful of lines, no design work, no protocol change, and it closes the entire drive-by case: an arbitrary page can no longer open a socket to your server at all. You already know the complete list of legitimate origins, because endpoint.ts is the only thing that builds the URL: http://localhost:1420 in development, tauri://localhost packaged, and the relay's origin later. Be aware of exactly what it buys: the RFC is blunt that “the intent is not to prevent non-browsers from establishing connections”, since a non-browser client simply sends whatever Origin it likes. So this is a fix for the realistic threat, not a security boundary.

Then a token, which is the real answer, and the one to think about. The requirement it has to satisfy is not "authenticate a user" — it is the one from lesson 2 and section 1 of this lesson: the same person reconnecting must present the same identity. That makes undo survive a drop, makes the leak collectable, and gives presence something stable to attach to. Which is why I would treat the token and the reconnect problem as a single piece of work rather than as security plus a bug: they are one missing concept.

The thing to be careful about is where the token travels. The browser WebSocket API gives you no way to set a request header, so the usual options are the query string, the Sec-WebSocket-Protocol header, or a first message after the socket opens. Each has consequences worth weighing before you pick — a query string ends up in logs, a subprotocol is awkward but is a real header, and a first message means a window in which the connection exists but has no identity.

And one thing it does not have to do: be a user account. Your requirement is continuity of identity across a reconnect, plus a way for the host to hand one out. Those are far weaker than a login, and building a login would be the expensive wrong answer.

06Recall

  1. Why does the client replay nothing after reconnecting?

    • The server would refuse stale commands
    • Replayed commands would arrive unordered
    • Absolute values could overwrite newer work
    • The pending edits were already discarded

    A place states a result computed against the board as it was before the drop. Replaying it would stamp on whatever changed while you were away. Option 4 is true but is a consequence, not the reason — the preview is discarded because the command will not be sent.

  2. What happens to umpire 3's undo stack after a reconnect?

    • It stays, and nothing can reach it
    • It is merged into the new umpire
    • It is dropped when the task ends
    • It is written into the save file

    Still in Doc::umpires, intact, keyed by an id no connection will present again. Both halves matter: the user silently loses undo, and the memory is never freed, because nothing removes an entry.

  3. Why does loopback binding not keep an attacker out?

    • The relay forwards external traffic in
    • Tauri exposes the port to the network
    • CORS headers override the bind address
    • The attacking code runs in the browser

    A page the umpire opens runs on their machine, so 127.0.0.1:7878 is reachable from it. Loopback excludes the network, and the threat is not on the network. Nothing about CORS or the relay is involved.

  4. What does the same-origin policy do for a WebSocket?

    • Blocks cross-origin sockets by default
    • Nothing, so the server must check
    • Requires a preflight before upgrading
    • Permits them once CORS headers allow

    It does not apply. No preflight, and CORS is never consulted, so the permissive CORS layer is neither the cause nor the cure. RFC 6455 §10.2 puts the duty on the server: verify Origin, answer 403 if you do not like it.

  5. What is the actual requirement a token has to meet here?

    • Proving which human is connected
    • Encrypting commands on the wire
    • Keeping one identity across reconnects
    • Stopping players reading the save

    Continuity is the requirement that undo, the leak and presence all share. Option 4 is a genuine goal but follows from identity rather than driving it, and a full login would be the expensive wrong answer to a weaker need.

07Drill: does this fix it?

For each proposal, pick the honest assessment.

  1. Tighten CORS to a single allowed origin.

    • Closes it, since all routes check origin
    • Moves the hole; the socket ignores CORS
    • Closes it for pages, not for native clients
    • Breaks nothing and prevents command sending

    It would stop a page reading /save, which is worth something — but commands travel over the socket, where CORS is not consulted at all. Your own comment already reaches this conclusion: being strict there "would only move the hole, not close it".

  2. Check the Origin header on upgrade.

    • Closes it fully, as the RFC intends
    • Useless, since any client may omit it
    • Breaks the packaged app's own origin
    • Closes the browser case, not other clients

    Exactly what §10.2 is for, and exactly as far as it goes: it stops malicious JavaScript in a trusted browser, and "the intent is not to prevent non-browsers from establishing connections". Not useless, not a boundary. Worth doing first because it is cheap and the browser case is the realistic one.

  3. Remove an umpire's entry when its connection closes.

    • Fixes the leak, admits undo is gone
    • Fixes both the leak and the history
    • Risks freeing an entry still in use
    • Requires the document write lock twice

    It stops the growth, and it is what was built. At the time I argued it pre-empted an unsettled question — whether a dropped connection really abandons that history. The owner settled it the other way, deliberately (ADR 0018): it does, even once identity exists. So this removal is not a stopgap, it is the policy.

08Read this next

RFC 6455, section 10, Security Considerations — short, and 10.2 is the paragraph that names your exact situation. Read 10.5 too, which is one sentence long and says the protocol “doesn't prescribe any particular way that servers can authenticate clients during the WebSocket handshake”. That is why there is no obvious right answer to find: the protocol genuinely leaves it to you, which is the thing worth knowing before you go looking for the standard pattern.
