Lesson 0002 · Kriegsspiel network model

The fan-out

One line of code wakes every connected umpire, and it sends them nothing. Everything interesting about this server is in that sentence.

00First, from memory

Two from lesson 1, before any new material. Answer without opening it.

  1. Why can HTTP not do what this project needs?

    • Its headers are too large
    • It cannot carry binary data
    • It drops messages under load
    • The server cannot speak first

    Client-initiated only. The server knows about the edit instantly and has no channel to mention it. Everything else — header overhead, connection churn — is a consequence of working around that one limitation with polling.

  2. What does a socket guarantee that this server spends?

    • Messages arrive in order
    • Messages arrive within deadline
    • Messages survive a disconnect
    • Messages are compressed first

    One TCP connection, so order is preserved. It is spent on sending image bytes and then immediately the addMap naming them, with no acknowledgement in between. Nothing about timing is guaranteed, and nothing survives a disconnect.

01The line, and the puzzle in it

self.changed.send_replace(());

crates/server/src/lib.rs:142

That is the whole of the fan-out. Look at what it sends: (). The unit type. No data. A channel that wakes every connection and hands each one nothing at all.

If your instinct is that a broadcast channel should carry the thing being broadcast, hold onto that instinct for two minutes — it is exactly the assumption this design rejects, and for a good reason.

So the question for this lesson is really two questions:

Why does the channel carry nothing? And what does each connection do when the doorbell rings?

02Why the channel carries nothing

Because there is no single message that would be correct for everybody. Two umpires connected to the same game can legitimately need different boards right now:

  • Umpire A is editing the live board. Umpire B is looking at turn 3 from ten minutes ago. Stepping turns is per umpire — viewing lives in Doc::umpires, not on the board.
  • Later, a player joins. They must receive a board with the other side's hidden units absent, not present-but-flagged. That is an architecture rule, not a preference: filter on the server.

Your own ADR says it in two sentences:

“Umpires viewing different turns, and later each side, see different boards, so one shared broadcast cannot work. A watch channel keeps only the latest change, so a slow client skips stale boards instead of queueing them.”

docs/adr/0021-each-connection-sends-its-own-snapshot.md

So the channel is a doorbell, not a delivery. It says something changed, go and look. Each connection then builds its own view from the document, under its own read lock, for its own umpire id.

The second half of that ADR sentence is the part people miss. watch is, in tokio's words, “a multi-producer, multi-consumer channel that only retains the last sent value”. Ring the doorbell five times while a connection is busy writing to a slow socket and it finds one pending notification, not five. It then sends one snapshot reflecting all five changes.

Tokio spells out the same property for wait_for: “the watch channel only keeps track of the most recent value, so if several messages are sent faster than wait_for is able to call the closure, then it may skip some updates.” For most channels that would be data loss. Here it is the whole point.

The property worth naming

Coalescing. A queue would make a slow client a growing memory liability and deliver it a backlog of boards that are already wrong. A watch channel makes a slow client simply skip frames. You already know this trade-off: it is the difference between queueing every input event and sampling the input state once per frame.

Note which side of the connection this protects: the server. The browser's WebSocket API has no equivalent — that is still an open exposure from lesson 1.

03What a connection does when the doorbell rings

Each connection is one client() task. Stripped to its skeleton:

async fn client(mut socket: WebSocket, game: Game) {
    let umpire = game.next_umpire.fetch_add(1, Ordering::Relaxed);
    // Subscribe before the first send, so a change made in between still wakes this loop.
    let mut changed = game.changed.subscribe();
    if game.send_view(&mut socket, umpire).await.is_err() { return; }
    loop {
        tokio::select! {
            message = socket.recv() => /* apply it, maybe reply */,
            Ok(()) = changed.changed() => /* send this umpire's view */,
        }
    }
}

crates/server/src/lib.rs:461–505

Four things are happening there and each one is a decision.

  1. An id per connection. Covered in lesson 1, and the reason this task can ask the document for its view rather than the view.
  2. Subscribe, then send. In that order, and the comment tells you why. A watch::Receiver only hears changes made after it subscribed. Reverse these two lines and you open a window: build the snapshot, someone else edits the board, then you subscribe — and that edit is never delivered to this client, which now shows a stale board until the next unrelated change happens to come along. A bug that appears only under concurrency, only sometimes, and only for one client.
  3. Send the first snapshot unprompted. Before the loop. The client asked for nothing; it gets the whole board the moment it connects. This is also the reconnection path — there is no separate "resync" message, because a fresh connection and a reconnection are literally the same code.
  4. Then wait on two things at once, for ever. That is tokio::select!, and it is the part worth slowing down for.

04select!, and the trap underneath it

Tokio's own one-line description:

“Waits on multiple concurrent branches, returning when the first branch completes, cancelling the remaining branches.”

tokio::select!

Read the emphasis again. Every time your client's message arrives, the half-finished changed.changed() future is thrown away. Every time the board changes, the half-finished socket.recv() is thrown away. Around the loop you go, and both are created fresh. In a busy game this happens thousands of times.

A detail worth knowing because it will confuse you in a debugger: “by default, select! randomly picks a branch to check first”. Deliberate — it stops one always-ready branch from starving the other. So the order you wrote the branches in is not the order they are polled.

So: is throwing away a half-polled future safe? That depends entirely on where the progress was being kept, and tokio gives this a name.

“Cancellation safety describes what happens when a future is dropped before it completes… If you have a future that has not yet completed, then it must be a no-op to drop that future and recreate it.”

tokio::select!, Cancellation safety

The rule in one sentence, and it is the transferable idea of this lesson:

The rule

If a future's progress lives in the future, dropping it loses that progress. If the progress lives in the object the future borrows, dropping it costs nothing.

Tokio's not-cancel-safe list is exactly the methods that accumulate into themselves: read_exact, read_to_end, write_all. Half a message read into a buffer that is about to be dropped is half a message gone — and tokio notes these “can lead to loss of data”. A partial read is not an error anybody reports. It is a corrupted stream, later.

Now prove it for these two branches

Branch 2, changed.changed(). Documented outright:

“This method is cancel safe. If you use it as a branch in tokio::select! and another branch completes first, then it is guaranteed that no values have been marked seen by this call to changed.”

watch::Receiver::changed

That last clause is the mechanism: "seen" is tracked on the receiver, not in the future. Drop the future and the receiver has not moved.

Branch 1, socket.recv(). Here is the interesting bit: axum does not document cancel safety for it. Its docs say only “Receive another message. Returns None if the stream has closed.” So you have to work it out. Three lines of axum's source settle it:

This is a skill, not a lookup. Most async libraries do not state cancel safety. You check: where does the state live? If the answer is "in the object", you are fine.

pub async fn recv(&mut self) -> Option<Result<Message, Error>> {
    self.next().await
}
// ...and WebSocket implements Stream, whose poll_next drives self.inner.

axum-0.8.9/src/extract/ws.rs:555 and :580

So recv() is just Stream::next(), and Stream::next appears on tokio's cancel-safe list. The reason is the rule above: next() holds nothing but a mutable borrow of the stream; every byte of partially-framed message state lives in self.inner, which outlives the future. Drop it mid-poll, recreate it next time round the loop, and not a byte is lost.

Both branches are cancel-safe, so the loop is correct. You can now say that with a reason, which is a different thing from having written it and seen it work.

05Three decisions hiding in plain sight

send_replace, not send

They differ in one way that matters: send “fails if the channel is closed, which is the case when every receiver has been dropped”, whereas send_replace “permits sending values even when there are no receivers”. Loading a save over POST /load with nobody connected is a perfectly ordinary thing to do, and it should not produce an error to handle.

The other half of the comment at lib.rs:140: it “wakes this connection too, which is how the sender gets its own board”. There is no special case for the umpire who made the edit. They are just another subscriber.

Effect::Me deliberately bypasses the channel

if game.receive(umpire, &text).await == Effect::Me
    && game.send_view(&mut socket, umpire).await.is_err()
{ break; }

crates/server/src/lib.rs:475–479

Stepping turns, or having a command refused, changes what one umpire should see. Pushing that through the watch channel would wake every other connection to rebuild and resend a board that has not changed — work and bandwidth for nothing. So the three values of Effect map onto three delivery routes: None → nobody, Me → this socket directly, Everyone → the doorbell.

The lock is released before the socket write

let snapshot = {
    let doc = self.doc.read().await;
    ServerMessage::Snapshot { board: doc.shown(umpire).clone(), /* ... */ }
};  // <- guard dropped here, before the await below
send(socket, &snapshot).await

crates/server/src/lib.rs:152–166

Two separate reasons, both worth being able to state. One: everything the snapshot needs is read under a single lock, so the board and the viewing index that labels it cannot disagree — no interleaved edit can land between reading one and reading the other. Two: the write to the socket happens with no lock held, because an umpire on hotel wifi must not be able to stall everybody else's edits. A held lock across an await on a network write is the classic way to turn one slow client into a frozen server.

The clone is the price. Roughly 20 KB per board at 200 units, per connection, per change — an estimate in your own ADR, never measured. Sending per-unit differences instead is the planned fix, and the reason to do it is this clone, not the bandwidth.

06Recall

  1. Why does the watch channel carry no data?

    • Boards are too large to send
    • No single board suits everyone
    • Channels cannot carry large structs
    • It would need another lock

    Umpires view different turns, and players will see filtered boards. There is nothing correct to put in one shared message, so the channel only says something changed and each connection builds its own view. Size is a separate concern and not the reason.

  2. What happens when the doorbell rings five times rapidly?

    • Five snapshots queue per client
    • The slowest receiver blocks senders
    • A slow client sees one wake-up
    • The oldest four are retried later

    watch “only retains the last sent value”, so notifications coalesce. A slow client skips stale boards rather than queueing them — it drops frames. Nothing blocks the sender, and nothing is retried.

  3. Why must subscribe() come before the first snapshot?

    • A change between them would be missed
    • The receiver count gates the send
    • Subscribing needs the document lock
    • The first snapshot marks values seen

    A receiver only hears changes made after it subscribed. Reversed, an edit landing in the gap is never delivered to this client, which then shows a stale board until some unrelated change arrives. Concurrency-only, intermittent, single-client: the worst kind of bug.

  4. What makes socket.recv() safe to cancel?

    • Axum documents it as cancel-safe
    • The socket buffers unread frames
    • Tokio restarts the dropped future
    • Its state lives in the stream

    recv is self.next().await, and the future holds only a borrow — all framing state is in the stream, which outlives it. Note option 1 is false: axum documents nothing of the kind, which is why you had to read the source.

  5. Why is Effect::Me not sent through the channel?

    • The sender cannot receive its own
    • Others would rebuild boards needlessly
    • Refusals must arrive before snapshots
    • The channel only wakes idle tasks

    Only one umpire's view changed, so waking every connection would have them all lock the document, clone a board and write it to a socket for no reason. Option 1 is the opposite of true — the sender is woken by the channel for Everyone, and that is how it gets its own board.

07Drill: what breaks?

The real test of understanding a mechanism is predicting its failure. For each change, pick the consequence.

  1. The document read lock is held across the socket write in send_view.

    • Snapshots can disagree with their labels
    • The connection misses later changes
    • One slow client freezes every umpire
    • Boards arrive in the wrong order

    A write to a stalled socket can block for a long time. Holding a read lock through it stops any writer taking the document, so no umpire anywhere can edit until that one client's network recovers. This is the single nastiest mistake available in this file.

  2. The two select! branches become a sequential await chain: receive a message, then wait for a change.

    • Changes only arrive after the client speaks
    • Both branches lose their cancel safety
    • The watch receiver stops coalescing
    • Commands are applied twice each

    The whole point of select! is waiting on both at once. In sequence, an idle client — one whose umpire is just watching — sits blocked on recv() and never reaches the changed() await, so it sees nothing until it happens to send something. Which is polling, reinvented.

  3. A branch is added that calls read_to_end on an upload instead of taking one binary frame.

    • Uploads become ordered after commands
    • The frame size limit stops applying
    • Image hashing moves onto the async worker
    • A cancelled read silently loses bytes

    read_to_end is on tokio's not-cancel-safe list: it accumulates into a buffer held by the future. The other branch firing drops that buffer mid-read. Tokio's phrasing is “can lead to loss of data”, and nothing reports an error — you get a corrupt image, or a stream out of sync, later.

  4. A player connection is added that receives the full unfiltered board and hides the other side in the browser.

    • The watch channel would need data
    • Opening devtools reveals hidden units
    • Snapshots would exceed the frame limit
    • Undo would stop being per umpire

    It arrived at the client, so the player has it — one devtools tab, or one saved network log, and the whole enemy order of battle is theirs. Hence the rule: filter on the server. This is also precisely why the channel carries no shared board.
