Lesson 0001 · Kriegsspiel network model

Why a socket, and not a request

An umpire in Berlin moves a piece. An umpire in Tokyo has to see it. Nothing in HTTP can do that, and the reason is worth knowing precisely, because the shape of the whole server follows from it.

01The question the transport has to answer

Your target scenario says umpires edit together, live, from anywhere in the world. Strip that down to one sentence of mechanism:

Berlin changed something. Who tells Tokyo?

In HTTP, nobody can. An HTTP exchange is client asks, server answers, and the server cannot speak first — it has no channel to speak into. The connection exists because the client opened it to ask a question, and once the answer is sent that is the end of it. The server knows about Berlin's edit immediately; it simply has no way to mention it to Tokyo.

This is the asymmetry to hold onto. Not “HTTP is slow” — HTTP is fine. The problem is that it is client-initiated only.

So with HTTP alone there is exactly one option left: Tokyo asks, over and over. Any change yet? Any change yet? That is polling, and it is what the WebSocket RFC was written to replace. The authors list three costs, and they are worth reading in their own words:

“The server is forced to use a number of different underlying TCP connections for each client… The wire protocol has a high overhead, with each client-to-server message having an HTTP header… The client-side script is forced to maintain a mapping from the outgoing connections to the incoming connection…”

“A simpler solution would be to use a single TCP connection for traffic in both directions.”

RFC 6455 §1.1, Background

There is a fourth cost the RFC does not spell out, and it is the one that matters most here: a latency floor. If Tokyo polls once a second, the average delay before Berlin's edit shows up is half a second, on top of the round trip. Poll ten times a second to fix that and you have multiplied every client's request load by ten, mostly to be told nothing has changed.

A graphics analogy that actually holds: polling is reading back from the GPU every frame to find out whether a draw finished. The cost is not the bandwidth. It is that you only ever learn at your own sampling rate.

02What a WebSocket actually is

Three facts, and they are all you need in order to read this codebase.

It starts as HTTP and stops being HTTP. The client sends an ordinary HTTP request carrying Upgrade: websocket. The server answers HTTP/1.1 101 Switching Protocols, and from that moment the same TCP connection carries WebSocket frames instead. The RFC is explicit that “any status code other than 101 indicates that the WebSocket handshake has not completed”, with normal HTTP semantics still applying. This is why your socket and your HTTP routes share one port: /ws is a route like any other, right up until it upgrades.

It is a thin layer over TCP. “Conceptually, WebSocket is really just a layer on top of TCP” (§1.5). What the layer adds is message framing: TCP gives you a byte stream with no boundaries, and WebSocket chops it into discrete messages, each one text or binary. “A message is composed of one or more frames.”

Without framing you would have to invent a length prefix to know where one JSON command ends and the next begins. The protocol does it for you, which is why ServerConnection can simply JSON.parse each event.data.

Everything TCP guarantees, you inherit. One connection, so messages arrive in the order they were sent, exactly once, or the connection breaks. Hold onto that one; section 3 spends it.

03Four properties, and the code that spends them

A socket is not free: it is a long-lived connection and a task per client. Here is what this project buys with it. Each one is a line of code you can point at.

Push: the server can start a conversation

// crates/server/src/lib.rs — after a command changed the live board
if effect == Effect::Everyone {
    self.changed.send_replace(());
}

crates/server/src/lib.rs:140–142

That wakes every connected client's task, and each one then sends its own fresh snapshot — including the umpire who caused the change. Nobody asked for it. This is the arrow HTTP cannot draw, and it is the whole reason the transport decision went the way it did. (Lesson 2 is about how that fan-out works.)

Order: two dependent messages, with no handshake between them

When you add a map, the client sends the image as raw bytes, then sends addMap naming that image's hash. The second message is useless if it arrives first. There is no acknowledgement, no retry and no state machine — and the comment in the server says exactly why:

The server does answer if the upload is refused (assetRejected). Only the happy path is silent: the client hashed the file itself, so a confirmation would tell it nothing it did not already know.

// A binary frame is an image being uploaded... The command that uses it
// follows as its own message, and a WebSocket keeps order, so the image is
// always in the store by the time that command is applied.
Some(Ok(Message::Binary(bytes))) => { /* ... */ }

crates/server/src/lib.rs:481–486

Over HTTP those would be two independent requests that can land in either order, so you would have to await the upload before issuing the command — a round trip you now do not pay. Ordering is a property you are deliberately spending, not a happy accident.

Identity: the connection is the session

// Every connection is a new umpire until umpires can identify themselves.
let umpire = game.next_umpire.fetch_add(1, Ordering::Relaxed);

crates/server/src/lib.rs:464

An HTTP server has no idea whether two requests come from the same person; that is what cookies and tokens are for. A socket does know: the connection is open, so while it lasts there is an obvious place to hang per-client state. Undo stacks live per UmpireId, and that id is handed out exactly once, here, when the socket opens.

The sting in the tail: if identity lives only in the connection, it dies with the connection. Reconnect and you are umpire 7 instead of umpire 3, and umpire 3's undo history is unreachable. A known gap in CLAUDE.md rather than an oversight — and it is lesson 4.

Cost per message: near enough nothing

No HTTP headers, no TLS handshake, no connection setup — a place command is a few dozen bytes of JSON in one frame. That is what makes it reasonable to send a command on every drag release rather than batching them, and what will make presence updates at roughly 20 a second affordable in step 5.

04So why is anything still HTTP?

Because the socket is the wrong tool for three of the things this server does, and the split is deliberate. From the top of lib.rs:

“Those are plain HTTP because a 16 MB map image belongs in something the browser can cache and a save belongs in something it can download, neither of which a WebSocket does for us.”

crates/server/src/lib.rs:3–6
Goes overWhatBecause
socketcommands, snapshotschanges to shared state; everyone needs them, unprompted
socket, binaryimage uploadmust be ordered before the command that names it
HTTP GET/assets/{id}large, immutable and addressable, so the browser caches it and three.js can just be handed a URL
HTTP GET/savethe browser's download machinery wants a response to a request
HTTP POST/loadone large body, one reply, no ordering constraint

The principle underneath transfers to any project: a socket is for events — small, ordered, pushed, perishable. HTTP is for resources — large, addressable, cacheable, requested. An asset id is the SHA-256 of the bytes, so /assets/{id} can never come to mean a different image, which is why the server can set Cache-Control: public, max-age=31536000, immutable and never think about it again. You cannot cache a socket message. You would not want to.

Note the direction split on images: up the socket, down over HTTP. Not an inconsistency — the upload needs ordering and the download needs caching, and each leg takes the transport that gives it that.

05Recall

Answer from memory before scrolling back up. Getting one wrong and seeing why is worth more to you than getting it right with the text still in view.

  1. Per RFC 6455, what does HTTP polling force the server to do?

    • Buffer every unread client message
    • Hold one lock per client
    • Use many separate TCP connections
    • Send its state as JSON

    §1.1: “The server is forced to use a number of different underlying TCP connections for each client.” The other two costs it lists are the per-message HTTP header, and the client having to map outgoing requests onto the incoming one. None of the three is about speed — they are all about the shape being wrong.

  2. What wakes a connection to resend its snapshot?

    • A poll from its client
    • The watch channel being written
    • A timer inside the loop
    • The document lock releasing

    self.changed.send_replace(()). There is no timer and no polling anywhere in this server: a connection sleeps until either its client says something or the board changes. Event-driven, not frame-driven — the opposite of your render loop.

  3. Why can the client send image bytes and then immediately send the command naming them?

    • The server acknowledges each upload
    • The client retries until accepted
    • Commands apply in any order
    • A socket preserves message order

    One TCP connection, so messages arrive in the order they were sent. The bytes are in the store before the command naming them is applied. Over two HTTP requests you would have to await the upload first. The guarantee replaces a round trip.

  4. Why are map images served over HTTP rather than the socket?

    • The socket cannot carry bytes
    • They change on every edit
    • The browser can cache them
    • The server compresses them first

    A socket message is an event that happens once; it has no URL, so nothing can cache it. An image has a content-hash id, so its URL is immutable and the browser keeps it for a year. Option 1 is simply false — the socket carries binary perfectly well, which is exactly how images go up.

  5. What identifies an umpire today?

    • A token the host issues
    • The open socket connection itself
    • A cookie set at login
    • Their place in the board

    A counter bumped once per connection. Convenient, and it is what makes per-umpire undo possible at all — but it means identity dies with the connection, so a reconnect loses undo history. Known gap, not an accident.

06Drill: which transport?

The skill, as opposed to the knowledge. For each one, decide before you click.

  1. An umpire drags three units into a line.

    • Socket
    • HTTP

    One place command, one undo step. A change to shared state that every other umpire must see unprompted: the definition of an event.

  2. A player's browser needs the 14 MB map image.

    • Socket
    • HTTP

    GET /assets/{id}. Large, immutable, cacheable, and handed to three.js as a plain URL. Pushing it down the socket would mean re-sending it on every reconnect.

  3. An umpire records a turn.

    • Socket
    • HTTP

    recordTurn. It changes the document, so every client's snapshot — and therefore its turn list — has to change. Event.

  4. The umpire clicks Save and wants a .ksg file on disk.

    • Socket
    • HTTP

    GET /save. The browser's download machinery is built around a response to a request; a socket message is not something it can offer as a file.

  5. An umpire uploads a new map image.

    • Socket
    • HTTP

    The catch. Up the socket as a binary frame, because addMap follows it and ordering does the job an acknowledgement would otherwise have to do. The same bytes come back down over HTTP. Different legs, different needs.

  6. A client reconnects and needs the whole current board.

    • Socket
    • HTTP

    Sent unprompted the moment the socket opens, before the loop even starts. Worth noticing that the first thing a connection does is push, with nothing having been asked of it.

07Read this next

RFC 6455, sections 1.1 to 1.5 — about three pages. Not the frame layout, not the masking rules: just the motivation and the overview. It is the highest-trust source there is on why this protocol exists, it is unusually well written for an RFC, and “I read the first three pages of the RFC” is a sentence that carries weight.

Then the practitioner's view of the authoritative-server model that a socket enables: Glenn Fiedler, What Every Programmer Needs To Know About Game Networking.

Keep the network model cheat sheet open while you read the code — it has the full message table and the socket lifecycle on one printable page.
